1. Project Overview

Campus Cab is a full-stack university ride-hailing platform that connects students with campus drivers. It supports two user roles — Students (who book rides) and Drivers (who accept and fulfill rides) — with real-time status tracking, email notifications, a safety SOS system, vehicle inspections, and a rating system.

Core Value Proposition

  • Zero platform fees — 100% of the fare goes directly to the driver
  • Campus-focused — designed specifically for university campuses with predefined locations
  • Safety-first — SOS button with GPS tracking, email alerts, and audit logging
  • Student-built — by students, for students

Why These Choices?

  • Next.js App Router — enables Server Components for faster initial loads and Server Actions for type-safe API calls without writing manual endpoints
  • Prisma + PostgreSQL — provides a strongly-typed schema that catches data issues at compile time; PostgreSQL handles the relational complexity of trips, users, and audit logs
  • NextAuth v5 — mature auth library with built-in session management, CSRF protection, and credential provider for email/password login
  • Zod — shared validation schemas used on both client (forms) and server (actions), ensuring consistency
  • Resend — simple, developer-friendly email API with React Email support
  • Capacitor — allows wrapping the same web app into native iOS/Android shells without maintaining separate codebases

Architecture Pattern

Server Actions over API Routes: The app primarily uses Next.js Server Actions (functions marked 'use server') instead of traditional REST API endpoints. This provides type-safe server calls directly from components without manual fetch calls, error handling, or loading states.

The application follows a layered architecture:

  1. Presentation Layer — React components and pages in src/app/ and src/components/
  2. Action Layer — Server Actions in src/lib/actions/ handle business logic
  3. Data Layer — Prisma ORM interacts with PostgreSQL
  4. Infrastructure Layer — Rate limiting, audit logging, email delivery

4. Database Schema & Models

The database uses PostgreSQL with Prisma as the ORM. The schema contains 16 models with UUID primary keys and snake_case column mapping.

Entity Relationship Diagram

Core Models

ModelPurposeKey Fields
User Base user account (both roles) email, passwordHash, role (STUDENT/DRIVER), passwordHintQuestion, passwordHintAnswer
Student Student-specific profile matricNo (unique), university
Driver Driver-specific profile driverId, isOnline, avgRating, totalTrips
Vehicle Driver's vehicle info make, model, color, licensePlate
Trip Ride booking record rideType, passengerCount, totalFare, status (5 states)
CampusLocation Pickup/dropoff points name, lat, lng
VehicleInspection Pre-ride safety checklist brakes, tires, lights, fireExtinguisher, firstAidKit, etc.
SafetyAlert SOS emergency records latitude, longitude, status (PENDING/ACKNOWLEDGED/RESOLVED)
Rating Post-ride driver rating score (1-5), feedback
AuditLog System-wide audit trail action, entity, entityId, details (JSON), ipAddress
PasswordResetToken Token-based password recovery token (hex), expiresAt, usedAt
PushToken Device push notification tokens token (unique), platform, isActive

Trip Status State Machine

PENDING ──→ ACCEPTED ──→ IN_PROGRESS ──→ COMPLETED │ │ │ └────────────┴──────────────┘ │ ↓ CANCELLED

Valid transitions: PENDING → ACCEPTED → IN_PROGRESS → COMPLETED. Any active state can transition to CANCELLED. Status history is tracked in RideStatusHistory.

Key Design Decisions

  • UUID primary keys — prevents ID enumeration attacks and works well with distributed systems
  • Separate Student/Driver models — keeps role-specific data isolated while sharing auth via User
  • Hint answers are bcrypt-hashed — even database admins cannot read the original answers
  • Cascade deletes — deleting a User removes their Student/Driver profile, trips, and notifications
  • Indexed fields — Trip(status, driverId, studentId), Notification(userId, isRead), AuditLog(entity, userId, action, createdAt)

5. Authentication System

Technology

Uses NextAuth.js v5 with the Credentials Provider for email/password authentication. Sessions are managed via JWT tokens (not database sessions).

Registration Flow

User fills registration form │ ▼ Server Action: registerStudent/registerDriver │ ├── Validate input (Zod schema) ├── Check rate limit (3 per 5 min) ├── Check for existing email/matricNo/driverId ├── Hash password with bcrypt (12 rounds) ├── Hash hint answer with bcrypt (10 rounds) ├── Create User + Student/Driver + Vehicle (transaction) ├── Log auth event (audit) └── Return success Password stored as: $2a$12$... (bcrypt hash) Hint answer stored as: $2a$10$... (bcrypt hash)

Login Flow

User enters email + password │ ▼ Server Action: loginUser │ ├── Validate input (Zod schema) ├── Look up user by email ├── Compare password with bcrypt └── Return result with code: • LOGIN_SUCCESS → NextAuth signIn() • ACCOUNT_NOT_FOUND • INVALID_PASSWORD → Shows "Forgot Password?" link • VALIDATION_ERROR NextAuth JWT callback: token.role = user.role token.userId = user.id

Session Management

  • JWT-based — session data stored in encrypted cookie, not in database
  • Role in token — role: STUDENT | DRIVER stored in JWT for fast authorization checks
  • Server-side checks — Layouts and Server Actions call auth() to verify sessions
  • Middleware — lightweight, only redirects / to /login; auth is checked in layouts

6. Password Recovery (Hint-Based)

Unlike typical email-link password resets, Campus Cab uses a security question (hint) system. During registration, users choose a question from 6 predefined options and provide a bcrypt-hashed answer. Recovery uses this hint to verify identity.

Predefined Security Questions

  1. What is your favorite food?
  2. What is your mother's maiden name?
  3. What city were you born in?
  4. What was the name of your first pet?
  5. What is the name of your best friend?
  6. What was the make of your first car?

3-Step Recovery Flow

STEP 1: IDENTIFY User enters email → Server looks up hint question (Returns generic question if account doesn't exist — prevents enumeration) ↓ STEP 2: VERIFY User selects question + enters answer → Server bcrypt-compares answer → If correct: generates 32-byte hex reset token (10-minute expiry) → Invalidates any previous unused tokens ↓ STEP 3: RESET User enters new password + confirmation → Server validates token (exists, not used, not expired) → Hashes new password with bcrypt (12 rounds) → Updates password + marks token as used (in transaction)

Security Features

  • Account enumeration prevention — always returns a hint question, even for non-existent emails
  • Answer hashing — hint answers stored as bcrypt hashes, not plaintext
  • Answer normalization — answers are trimmed and lowercased before hashing/comparison
  • Token expiry — 10-minute window prevents stale token abuse
  • Single-use tokens — previous tokens are invalidated when a new one is generated
  • Client-side validation — per-question format validation (letters-only for names, any text for food)
  • Collapsible hints — forgot-password page shows the full list of predefined questions as a reference

Client-Side Hint Validation

The validateHintAnswer() function in validations.ts applies per-question rules:

  • All answers: 2-50 characters
  • Name/city/pet/friend/car questions: only letters, spaces, hyphens, apostrophes
  • Food question: any text allowed

Ride Types

Booking Flow (Student Side)

Student opens /student/book │ ├── Selects pickup location (from 4 campus locations) ├── Selects drop-off location ├── Chooses ride type (Solo / Shared) ├── Sets passenger count (1-10) └── Clicks "Book Ride" │ ▼ Server Action: createTrip │ ├── Validate (Zod schema) ├── Rate limit check (10 per 5 min) ├── Verify pickup ≠ dropoff ├── Calculate fare (₦800 × passengers) ├── Create Trip (PENDING) + TripPassenger ├── Record RideStatusHistory ├── Notify all online drivers (in-app notification) └── Audit log

Trip Lifecycle

EventTriggered byActions
CreatedStudentTrip set to PENDING. Notifications sent to all online drivers.
AcceptedDriverTrip set to ACCEPTED. Driver assigned. Student notified + emailed.
StartedDriverTrip set to IN_PROGRESS. Student notified + emailed.
CompletedDriverTrip set to COMPLETED. Driver's totalTrips incremented. Student notified + emailed. Rating prompt.
CancelledStudent or DriverTrip set to CANCELLED. Other party notified + emailed. 30-second grace period for students.

Key Trip Features

  • Fare calculation — ₦800 per passenger (configurable constant)
  • Grace period — students can cancel within 30 seconds without penalty
  • Concurrent booking protection — Prisma transaction ensures only one driver can accept a PENDING trip
  • Real-time tracking — ActiveRideTracker component polls for status updates
  • Status history — every status change is recorded with timestamp and actor

Vehicle Inspection Checklist

Drivers must complete an 8-point inspection before going online. All items are required:

  1. ✅ Brakes functional
  2. ✅ Tires in good condition
  3. ✅ All lights working
  4. ✅ Interior clean
  5. ✅ No trash
  6. ✅ Fire extinguisher present
  7. ✅ First aid kit present
  8. ✅ Fuel/Battery above 50%

Driver Registration

Driver registration collects additional vehicle information:

  • Driver ID (unique identifier)
  • Vehicle make, model, color
  • License plate number
  • Password hint question + answer (same 6 predefined questions as students)

9. Safety Features (SOS)

SOS Button

Available on the student dashboard during active rides. When triggered:

  1. Confirmation dialog — prevents accidental activation
  2. GPS capture — requests browser geolocation (5-second timeout)
  3. Alert creation — creates SafetyAlert record with coordinates
  4. Email to admin — sends emergency email with user info, location (Google Maps link), and ride details
  5. Confirmation email — sent to the student confirming the alert was recorded
  6. Audit log — records the SOS event with full context

SOS Email Content

  • User name and email
  • Timestamp
  • GPS coordinates with Google Maps link
  • Active ride information (pickup/dropoff)
  • Action required notice
Rate Limiting: SOS is rate-limited to 3 triggers per 10 minutes to prevent abuse. The SOS button is also available in the ride tracker component during active rides.

RIDE_STARTEDDriver starts rideBooking student
RIDE_COMPLETEDDriver completes rideBooking student
RIDE_CANCELLEDEither party cancelsOther party

Email Notifications (Resend)

Six email templates are provided, all using a branded HTML template:

  1. Ride Accepted — driver name, pickup/dropoff, fare, passenger count
  2. Ride Started — driver name, route, safety reminder
  3. Ride Completed — trip summary, rating prompt
  4. Ride Cancelled — cancellation notice with who cancelled
  5. SOS Alert — emergency details with GPS and ride info
  6. SOS Confirmation — confirmation to the person who triggered SOS
Non-blocking emails: All email sends are wrapped in .catch(() => {}) so they never block the main operation or cause user-facing errors if the email service is down.

Push Notifications

The app includes Capacitor push notification support via @capacitor/push-notifications. Push tokens are stored in the push_tokens table and managed via the PushNotificationProvider component.

11. Security & Rate Limiting

Rate Limiter

An in-memory sliding window rate limiter protects all sensitive endpoints:

ActionLimitWindow
Login5 attempts1 minute
Registration3 attempts5 minutes
Booking10 requests5 minutes
SOS3 triggers10 minutes
Rating20 submissions5 minutes
Password Reset5 attempts1 minute
API60 requests1 minute
Production Note: The in-memory rate limiter resets on serverless cold starts and doesn't share state across Vercel's distributed instances. For production-grade rate limiting, replace with Redis-backed @upstash/ratelimit.

Security Measures

  • Password hashing — bcrypt with 12 salt rounds
  • Hint answer hashing — bcrypt with 10 salt rounds (answers never stored in plaintext)
  • Zod validation — all inputs validated on both client and server
  • CSRF protection — NextAuth handles CSRF tokens automatically
  • JWT sessions — encrypted session cookies, not database-stored sessions
  • Server Actions — no exposed API endpoints for sensitive operations
  • Rate limiting — all auth and booking endpoints are rate-limited
  • Account enumeration prevention — forgot-password always returns a question
  • Single-use reset tokens — previous tokens invalidated on new request
  • Input sanitization — trim, lowercase normalization on emails and answers

12. Audit Logging

Every significant action is recorded in the audit_logs table for compliance and debugging:

CategoryActions Logged
Tripcreated, accepted, started, completed, cancelled
Safetysos.triggered, sos.acknowledged, sos.resolved
Authauth.login, auth.register, auth.logout, auth.password_reset_request, auth.password_reset_complete
Driverdriver.went_online, driver.went_offline, driver.inspection_submitted
Ratingrating.submitted

Audit Log Entry Structure

{
  userId:     "uuid"     — who performed the action
  action:     "string"   — action type (e.g., "trip.accepted")
  entity:     "string"   — entity type (e.g., "Trip")
  entityId:   "uuid"     — specific entity ID
  details:    { ... }    — JSON context (from/to states, fare, locations)
  ipAddress:  "string"   — client IP from headers
  createdAt:  timestamp  — auto-generated
}

All audit logging is fire-and-forget — errors are caught and logged to console, never blocking the main operation.
